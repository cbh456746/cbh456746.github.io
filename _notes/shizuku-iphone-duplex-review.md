**시즈쿠의 아이폰 실험과 Shizuku-Duplex는 별개의 발표다.** 이 글은 두 발표의 기술 스택을 나눠 살펴보고, 전이중 대화에서 사용자가 끼어들 때 실제로 확인된 동작을 정리한다.

## 먼저, 서로 다른 두 발표를 구분하자

“아이폰 안에서 시즈쿠와 대화한다”는 [ASCII.jp 기사](https://ascii.jp/elem/000/004/449/4449767/)에서 가장 눈길을 끈다. 그런데 기사에는 **11월 5일의 아이폰 단독 시제품**과 **11월 8일의 Shizuku-Duplex 발표**가 함께 나온다. 두 기술을 하나의 모바일 제품으로 받아들이면 실제로 검증된 범위를 넘어서게 된다.

| 발표 | 공개된 작동 방식 | 확인되지 않은 연결고리 |
| --- | --- | --- |
| 아이폰 단독 실험 | 음성 인식 → 경량 언어 모델 → 음성 합성을 아이폰에서 처리 | 여기에 Shizuku-Duplex가 쓰였는지 |
| Shizuku-Duplex | 듣기와 말하기를 동시에 이어가는 전이중 음성 대화 모델 | 이 모델이 아이폰에서 실행되는지 |

[아이폰 시제품 영상 보기](https://x.com/ShizukuResearch/status/2118176686676348984) (X 로그인이 필요할 수 있음) · [Shizuku-Duplex 공식 기술 설명과 데모 보기](https://shizuku.ai/en/blog/1/)

## 아이폰 속 시즈쿠: 음성 파이프라인을 기기 안으로

아이폰 시제품의 흐름은 비교적 익숙하다. 사용자의 말을 **음성 인식**이 글로 바꾸고, **경량 언어 모델(LLM)**이 답을 만든 뒤, **음성 합성**이 시즈쿠의 목소리로 읽는다. 핵심은 이 세 단계를 클라우드 요청 없이 아이폰 안에서 처리했다는 점이다. 개발 설명에는 GPU와 Neural Engine을 활용한다고 나온다. 모델을 가볍게 만든 만큼 평소 시즈쿠보다 대화 능력이 낮다는 설명도 붙었다. [출처: ASCII.jp 기사](https://ascii.jp/elem/000/004/449/4449767/)

이 실험은 “캐릭터와의 음성 대화를 로컬에서 구현할 수 있다”는 가능성을 보여준다. 다만 기기 모델, 사용한 음성 인식·언어·합성 모델의 이름, 앱 용량, 메모리 사용량, 배터리와 발열은 공개 자료만으로 알 수 없다. **아이폰 시제품의 오프라인 작동**을 근거로 **Shizuku-Duplex도 아이폰에서 작동한다**고 말할 수는 없다.

## Shizuku-Duplex: 대화의 차례를 기다리지 않는 구조

전통적인 순차형 음성 챗봇은 대체로 사용자의 말이 끝났다고 판단한 다음 음성 인식, 답변 생성, 음성 합성을 차례로 실행한다. 이 구조만으로는 AI가 말하는 도중 사용자가 끼어들거나, 짧게 “응” 하고 맞장구칠 때 자연스럽게 반응하기 어렵다. 별도의 중단·재시작 제어가 필요하다.

[Shizuku AI의 기술 설명](https://shizuku.ai/en/blog/1/)에 따르면 Duplex는 **80ms마다 한 번씩** 사용자 음성을 받아 처리하고 다음 출력을 결정한다. 말하는 동안에도 입력을 계속 듣는다. 음성 입력은 스트리밍 오디오 인코더를 지나 LLM 기반 Transformer에 들어가고, 모델은 앞선 순간의 출력과 함께 새 입력을 해석한다.

```text
사용자 음성 → 스트리밍 오디오 인코더 → LLM 기반 대화 모델
                                         ├─ 텍스트 → 다음 발화의 내용
                                         ├─ 오디오 토큰 → 디코더 → 시즈쿠의 음성
                                         └─ 동작 신호 → Live2D 캐릭터 움직임
```

모델은 실제 음성보다 조금 앞서 발화 내용을 텍스트로 만들고, 음성 토큰과 동작 신호도 출력한다. 덕분에 답의 내용, 말하는 타이밍, 캐릭터의 움직임을 같은 대화 흐름 안에서 다룬다. **80ms는 처리 주기이지, 사용자가 80ms 만에 답을 듣는다는 뜻은 아니다.** 이 주기를 맞추기 위해 개발팀은 TensorRT와 Triton 커널을 사용했다고 설명한다. [출처: Shizuku AI 기술 설명의 작동 원리와 모델 구조](https://shizuku.ai/en/blog/1/)

### 사용자가 끼어들면 실제로 무엇이 멈추나

가장 중요한 장면은 AI가 말하는 도중 사용자가 새 질문을 시작할 때다. Duplex는 발화 중에도 사용자 음성을 듣고 있으므로, 뒤이어 들어오는 음성을 다음 처리 주기에 반영해 **현재 음성 출력을 멈추고 새 입력에 반응**할 수 있다. 반대로 사용자의 짧은 맞장구에는 AI가 말을 이어가는 동작도 시연한다. 따라서 단순히 “마이크에 소리가 들어오면 무조건 중단”하는 규칙보다, **새 발화와 맞장구를 구분하는 대화 제어**에 가깝다. [출처: 공식 끼어들기·맞장구 데모](https://shizuku.ai/en/blog/1/)

여기서 **음성 출력의 중단**과 **내부 답변 생성 작업의 취소**는 구별해야 한다. 공식 자료는 전자를 데모와 평가로 보여주지만, 사용자가 말하기 시작한 순간 생성 중이던 텍스트·오디오 작업을 어느 범위까지 취소하는지까지는 공개하지 않는다. 사용자의 표현대로 “AI 답변 생성을 중단하고 사용자 입력을 수행한다”는 것은 **사용자에게 보이는 동작을 설명하는 말**로는 적절하지만, 내부 구현을 확정하는 문장으로 쓰기는 어렵다.

개발사 평가에서는 사용자 끼어들기 후 **2초 안에 발화를 멈춘 비율이 89%**였다. 즉 끼어들기 대응이 구현되었지만, **항상 즉시 멈추는 것은 아니다.** 같은 평가에서 다른 사람에게 건넨 말에 응답한 비율은 **83%**여서, “지금 나에게 말한 것인가”를 구분하는 문제도 남아 있다. 이 수치는 개발사 자체 평가이며 독립적인 실사용 검증으로 받아들여서는 안 된다. [출처: Shizuku AI 평가](https://shizuku.ai/en/blog/1/)

### 검색 중에도 대화를 이어가는 방법

복잡한 질문이나 웹 검색은 매 80ms 안에 끝내기 어렵다. Duplex는 **대화 모델**과 **백그라운드 모델**을 분리한다. 대화 모델이 필요할 때 `DELEGATE`라는 신호로 작업을 넘기고, 백그라운드 모델이 검색하는 동안에도 사용자와의 대화를 이어간다. 결과가 돌아오면 그 내용을 다시 대화에 반영한다. 긴 대화에서는 약 5분마다 이전 내용을 요약해 문맥을 다시 구성하는 방식도 설명한다. [출처: 공식 아키텍처와 문맥 관리](https://shizuku.ai/en/blog/1/)

## 이 기사가 보여준 진전과 아직 남은 질문

내가 주목한 것은 답을 빨리 만드는 기술 자체보다 **언제 듣고, 언제 멈추고, 언제 다시 말할지**를 모델이 음성 및 캐릭터 동작과 함께 처리한다는 점이다. AI 버튜버의 설득력은 좋은 문장 하나뿐 아니라 대화의 박자에서 나온다. Duplex는 바로 그 박자를 기술의 중심에 놓았다.

동시에 두 발표를 합쳐 **“아이폰 한 대에서 완전한 전이중 시즈쿠가 돌아간다”**고 결론 내리기에는 이르다. 현재 공개된 자료에서 두 시스템의 통합, 모델 가중치·코드의 공개 여부, 아이폰 최소 사양과 저장 공간을 확인할 수 없다. 다음 발표에서는 실제 기기에서 끼어들기 정확도와 장시간 구동 성능까지 볼 수 있으면 좋겠다.
